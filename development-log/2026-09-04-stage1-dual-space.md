# 起點

owner 給了第一關的構想：一名玩家撿起牆上的護目鏡，啟動之後世界變成異世界；
中段跑酷的柱子間隔刻意大於一次跳躍的距離，**過去的方式是切換空間**，踩另一個
空間才有的落腳點；最後在異空間房間拿到鑰匙，拿完地板開始鬆動。

在這之前 repo 只有「平台 + 兩個玩家 + 落後者優先鏡頭」，沒有任何互動物件、
沒有關卡狀態、關卡資料只有單一組平台。

owner 拍板的四項：

|---|---|

| 本輪範圍 | 機制 + 護目鏡與鑰匙拾取（崩塌與過關條件下一輪） |

## 草圖的讀法（可能讀錯，已回報給 owner）

左邊封閉房間 → 牆上護目鏡 → 五根越來越高的柱子 → 最右邊最寬的是高點。
每根柱子上方有一條短的浮空細線，讀成「另一個空間的落腳點」。

但草圖上那些細線幾乎正對在柱子正上方（只高 50~60），那樣的話它給的是**高度**
不是**水平距離**，跨不過柱子之間的缺口。所以實作把異空間的落腳點放在**缺口
正中間**，機制才成立。如果 owner 要的是「同一根柱子在另一個空間比較高」那種
讀法，程式碼一樣、只有 JSON 數字會不同。

## 步驟 21：封閉房間本身就是教學關

排關卡時想通的一件事，寫下來是因為它改變了關卡的結構：

**草圖左邊那個封閉房間不需要另外做教學。** 護目鏡在牆上，而那面右牆
（`RoomWallR`）只存在於正常空間 —— 撿到護目鏡、切到異空間，牆消失，就走出去了。
機制第一次使用就是用來解自己的謎。

牆高 450（y 550→1000），跳躍高度只有 300.5，所以跳不過去；落差表的第 0 列
會把這件事印出來（`爬升 450 > 跳躍高度`），等於順便斷言了「房間真的是封閉的」。

## 步驟 22：空間模型 —— 切換的是玩家的 mask，不是平台的 layer

```
collision layer bit 1（值 1）= 正常空間的平台
collision layer bit 2（值 2）= 玩家（現況，不動）
collision layer bit 3（值 4）= 異空間的平台
兩邊都存在的平台 = 1 | 4 = 5
```

平台的 `collision_layer` 設定一次之後**永不改變**，切換空間改的是**兩個玩家的
`collision_mask`**（1 ↔ 4）。三個理由：

1. 兩個空間永遠都查得到 → 切換前的卡牆預檢才有東西可查。反過來做（切換時開關
   平台的 layer）的話，非作用空間的平台在物理世界裡等於不存在，預檢會查不到。
2. 空間狀態只有 `_active_space` 一個變數，其餘全部由 `_apply_space()` 推導
   （AGENTS.md：同一份狀態不要開兩個欄位）。
3. **完全不用改 `player.gd` / `player.tscn`** —— `collision_mask` 是
   CharacterBody2D 的內建屬性，由 Level 直接寫（架構約束 2：父推子）。
   那兩個檔案是美術那輪的地盤，這輪一個字都沒動。

## 步驟 23：切換前的卡牆預檢

站在「另一個空間有實體」的位置上切換會卡進幾何裡。處置是**擋下切換**，
不是切了再讓物理把人推出來 —— 那會把人彈到奇怪的地方，而且是靜默的。

`get_world_2d().direct_space_state.intersect_shape()` 對目標空間的 layer 查兩個
玩家各一次。查詢矩形從玩家自己的 `CollisionShape2D` 讀出來再縮 2 單位，
**不寫死 60x88** —— 那會變成碰撞箱尺寸的第二份拷貝。

只擋「會卡進實體」，不擋「腳下的地板會消失」。後者是這個機制的核心風險，
玩家要自己承擔。

## 步驟 24：幾何斷言從「單空間地面列」換成「跨空間 x 投影聯集」

舊的 `_validate_gaps()` 檢查同高地面列的相鄰缺口 ≤ `MAX_GAP = 350`。
新關卡的柱子間隔**故意**做到 620（理論極限約 506，跨不過去），舊斷言會整排
FAIL —— 不是 bug，是斷言的語意過期了。

新的硬斷言：把所有平台（不分空間）在 x 軸上的投影取聯集，不得存在一段長度
> `MAX_GAP` 的區間是「兩個空間都沒有落腳面」的。

`ground_y` 這個欄位因此沒有人讀了，**從 JSON 拿掉**（AGENTS.md：不要留誤導性
的死欄位）。

兩個已知的寬鬆處，寫在程式碼註解裡而不是假裝沒有：

1. 牆（高而窄、踩不到頂）也會貢獻 x 覆蓋，所以有牆的區段這條會比實際寬鬆。
   這一關的牆都站在地板上，地板本身已經覆蓋那段 x。
2. 垂直方向不斷言 —— 維持 plan-v5〈這輪不做〉#17，爬升靠落差表給人眼掃。

### 落差表一開始說了謊

第一次跑出來的表有這一列：

```
1  RoomWallL both  (0,550) -> (1040,550)  980  0  同空間跨不過 → 需切換
```

左牆到右牆的 980「缺口」根本不存在，`RoomFloor` 從 0 鋪到 1100，整段都踩得到。
成因是表格按 x 相鄰比對，而牆疊在地板的 x 範圍內。

**處置：讓表格與斷言共用同一份計算。** 抽出 `_compute_uncovered_spans()`，
表格只在「這段 x 真的沒有任何落腳面」時才標「需切換」。各算一次的話，兩個報表
遲早會說出互相矛盾的話。

## 步驟 25：拾取物與關卡狀態

拾取物是 `Area2D + ColorRect`，`collision_mask = 2`（玩家那個 bit），接
`body_entered`。**物理訊號不受架構約束 1 影響** —— 那條限制的是輸入回呼
（`_input` / `_unhandled_input` / `_gui_input`），物理訊號在裸掛的 SubViewport
底下照常運作。

沒有另開 `pickup.gd`：撿沒撿到本來就屬於關卡狀態，拆出去反而變成兩個地方各存
一份。狀態只有 `_goggles_holder`（-1 = 沒人撿到，不另外開 `_goggles_taken`）
與 `_key_taken`，節點每次由 `_refresh_pickups()` 從這兩個變數重繪。

一個 Godot 的坑：`monitoring` 不能在 `body_entered` 的回呼裡直接寫，引擎會擋下
「訊號派送中修改監聽狀態」。走 `set_deferred()`。

### 重置必須連關卡狀態一起重置

`_reset_all()` 原本只把兩個人送回出生點。加了關卡狀態之後如果不一起清，
出界重生會變成「人在起點，但護目鏡已經不見了、世界還停在異空間」——
**關卡直接壞掉，而且不會報錯**。這類「不崩潰但靜靜地歪掉」的東西是這個專案
一路上最貴的 bug 型態。

## 步驟 26：3D 背景跟著換色

`background_3d.tscn` 的三層方塊各共用一份 `StandardMaterial3D` sub-resource，
加上一個 `Environment` 和一盞 `DirectionalLight3D` —— 改 5 個 color 屬性就換掉
整個色調，不需要碰 24 個 MeshInstance3D。

接線走既有的模式：`Level` 發 `space_changed`（過去式命名，傳 `StringName`
而不是 enum，背景層因此不需要認識 Level 的型別），`Main._ready()` 接到
`Background3D.on_space_changed()`。

**正常空間那組顏色不寫在程式碼裡**，開場時從場景讀下來存著。這樣
`background_3d.tscn` 仍然是「正常空間長什麼樣」的唯一來源，切回去是還原場景的
值，不是還原一份拷貝。

第一次 `space_changed` 必須在 `Level.activate()` 裡發，不能在 `_ready()` ——
接線是 `Main._ready()` 才做的，`_ready()` 裡發等於發給沒有人聽（架構約束 2）。

這踩到 plan-v5〈這輪不做〉#15「3D 背景的動態內容」的邊。主張是：一次性的靜態
色組切換不是動畫/粒子/天空盒/動態光照。**這一項待 owner 認可**，不認可就整段砍掉，
其他不受影響。

## 步驟 27：`class_name Level` 與 `class_name Background3D`

`main.gd` 原本把 `_level` 標成 `Node2D`，`_level.activate()` 是靠 unsafe access
混過去的。要接 `space_changed` 這條 signal 就不行了 —— signal 不像 method，
在靜態型別上找不到會直接是錯誤。

所以兩個腳本都補上 `class_name`（跟 `Player` / `SharedCamera` 的慣例一致），
`main.gd` 的兩個 `@onready` 改成實際型別。順帶把原本那兩處 unsafe access 也修掉了。

## 步驟 28：配色是實測改的，不是憑感覺調的

第一版用 `GHOST_ALPHA = 0.22`、平台顏色沿用舊的 `Color(0.30, 0.34, 0.42)`。
截圖出來**跑酷段完全讀不出來**：3D 背景是大塊方塊、亮度落在 0.2~0.35，玩法幾何
跟它同一個亮度帶，分不出哪塊踩得到；幽靈預覽在忙的背景前面等於看不見。

那不是美感問題是功能問題 —— 這個機制要玩家判斷「等一下要落在哪」。

改成：三個平台顏色一起提亮到 0.5~0.7 的亮度帶（**用亮度把兩層分開，用色相區分
三種平台**），`GHOST_ALPHA` 0.22 → 0.38。重拍之後兩個空間都讀得懂了。

順帶一提，`both` 的暖灰色效果最好 —— 它兩個空間都不變，是玩家在畫面上唯一
不會動的定錨點。這三個都是草稿值，改常數不影響任何邏輯。

## 步驟 29：出界重生保留拾取物 —— 一次試玩就暴露的代價

owner 第一次試玩的 session log：

| 事件 | 次數 |
|---|---|
| 撿到護目鏡 | **7** |
| 切換空間 -> alt / normal | 6 / 4 |
| 切換被擋下 | **0** |
| 重置(出界) | 5 |
| 重置(R 鍵) | 10 |
| 鑰匙到手 | **0** |

零 error 零 warning，機制本身都有動。但**護目鏡撿了 7 次、鑰匙 0 次**：
每摔一次，開場整段要重來一遍。

成因是步驟 25 的 `_reset_all()` 會把關卡狀態一起清掉。當初「兩人一起回出生點」
是在**還沒有任何關卡狀態**的時候拍板的（上一份 dev-log 步驟 15），
現在多了拾取物，那條規則的代價就變成「跑酷失手一次，罰你重看一次教學」。

owner 拍板：**保留護目鏡，位置回出生點。**

實作上把兩條路徑分開，差別只有一個 `clear_pickups` 參數：

- **出界**（false）—— 位置與空間回開場，拾取物保留
- **R 鍵**（true）—— 除錯用，連拾取物一起清，真的回到開場

這不是推翻步驟 15「出界與 R 是同一個行為」那個決定 —— 那條的理由是鏡頭
（N4 的前提消失了），而當時還沒有拾取物。這是把它延伸到一個當時不存在的情況。

**空間仍然一定要重置**：不重置的話重生會變成「人在起點，但世界還停在異空間」，
而封閉房間的右牆只存在於正常空間 —— 開場直接壞掉而且不報錯。

另外「切換被擋下」實戰 0 次，代表卡牆預檢不礙事，但也代表它只有診斷腳本驗過。

# 環境知識

  `/c/Users/Kila/AppData/Local/Programs/Python/Python313/python.exe`。
- `godot --headless --path . --quit-after 20` 可以只跑幾幀就退出，用來拿載入期

  `Input.action_press()`，截圖則**不能加 `--headless`**（dummy renderer 產不出圖）。

- `InputMap.event_is_action()` 可以在不按鍵的情況下問「這個事件會打中哪個 action」，
  用來驗 `location` 之類的綁定假設很直接。
