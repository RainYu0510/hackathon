另開一份是因為這輪的主題不同：那份是玩法層與匯出鏈，這份是美術管線。

# 起點

玩家角色一直是 `ColorRect`，專案裡沒有任何美術資產。手上有 AI 產出的
8 格黑貓跑步接觸表（contact sheet），要把它變成 Godot 能用的精靈圖。

owner 的要求是**可以 vibe coding** —— agent 能反覆迭代的形式，不是 GUI 操作。

# 為什麼不是 Aseprite

Aseprite 確實能自動化（`-b` 批次 CLI 加 Lua Script API），但它的
Import Sprite Sheet **假設你已經有等距網格**。AI 算出來的接觸表不是：
有編號標籤列、格距不均、腳底基準線不齊、還焊了一條地面陰影橫條。

這些都得先處理掉才輪得到那類工具。所以寫 `tools/make_spritesheet.py`
做「先處理掉」的部分，Aseprite 的定位是管線跑完之後的手工修圖。

只用 stdlib `zlib` + numpy，不裝 Pillow —— 這台機器 numpy 有、Pillow 沒有，
而 PNG 讀寫加起來不到一百行，沿用 `tools/serve.py` 只用 stdlib 的風格。

# 一個一開始就講錯、後來被實測推翻的判斷

最初建議「量測原生像素區塊大小 → nearest-neighbor 還原」。實測水平
run-length 的 **GCD = 1**，主要 run 長度散在 2/3/4 之間 —— 這不是整數倍
放大的像素圖，是帶抗鋸齒的「偽像素風」算圖。**沒有原生像素網格可以還原。**

所以降取樣改成 premultiplied box filter + alpha 二值化。

# 變更內容

## 步驟 16：管線第一版與兩個當場被實測推翻的設計

計畫裡寫的兩件事，跑第一次就發現是錯的：

### 陰影偵測不能逐格判

計畫寫「每格從 bbox 底往上掃寬度落差」。實跑之後**格 1 和格 7 都偵測失敗**：

- 格 7 有揚塵特效，寬 118-120px，跟陰影一樣寬
- 格 1 底部有個 5px 殘屑，會讓「從底往上掃」立刻短路

改成**跨 8 格取中位數寬度、一次判定共同地平線**。中位數對「某格有特效」跟
「某格抬腳騰空（寬度為 0）」兩種干擾都免疫。實測中位寬在 local y=293 是 10、
y=294 跳到 106，一個數量級的落差，8 格判定一致。

### 垂直對齊會把跑步循環壓平

計畫寫「以剝完陰影的 bbox 底（腳底）對齊到共同基準線」。但實測
**8 格的頭頂本來就齊平（top y=10~11），動的只有腳** —— 格 4、5 是騰空幀，
腳底比其他格高 16-17px。按各自腳底重新對齊 = 把騰空的腳硬拉回地面，
抬腳幅度整個消失。

改成**共用裁切視窗**：地平線共用，每格保留自己相對於它的位移。

## 步驟 17：22px 太糊 → render_divisor 4 改 2

第一版依 owner 決定產在 22px（貼圖 = 碰撞箱，88 世界單位 ÷ divisor 4）。
結果角色的細節量（墨鏡、球鞋、連帽衫）在那個尺寸糊成一團，辨識不出是貓。

**這不是管線的問題，是設計與解析度不匹配。** 這隻貓照 48-64px 的規格畫，
22px 只夠表達剪影加 1-2 個特徵（紅白機馬力歐就是 16px，沒有臉部細節）。

角色螢幕高度 = `88 / render_divisor`。可用值**只有 {1, 2, 4, 8}**：必須同時
整除 88（角色高）與 1920/1080（畫面），否則貼圖對不齊像素格。88 的因數與
gcd(1920,1080)=120 的因數取交集就是這四個。**沒有 divisor 3 這個中間選項。**

owner 選 2 → 角色 44px。連帶改動：管線 `--height 44`、`player.tscn` 的
`scale` 4→2。物理常數、關卡 JSON、`MAX_GAP`、鏡頭數學都沒動 ——
世界座標一個都沒變，`half_w` 仍恆為 960。

### 貼圖對位是整數關係，不是眼睛喬的

```
cell 40x46 art px，角色內容佔第 1..44 列（上下各留 1px）→ 垂直置中
render_divisor = 2，所以 1 art px = 2 世界單位
scale 2 → 內容 44 * 2 = 88 世界單位高，與碰撞箱的 88 完全吻合
```

節點放原點、`centered` 用預設的 true 就對齊，不需要 offset。
headless 實測印出：內容 y `-44..44`，碰撞箱 y `-44..44`。

**這三個數字（`render_divisor` / `--height` / `sprite scale`）是綁在一起的。**
只改其中一個畫面不會報錯，只會靜默地把角色畫成錯的大小 —— 那種 bug 很難
從畫面反推。所以 `Player._ready()` 加了 `_assert_sprite_matches_hitbox()`。

## 步驟 18：Godot 綁定與兩人配色

`player.tscn` 的 `ColorRect` 換成 `AnimatedSprite2D`。SpriteFrames 由管線
一併產出（`--godot-frames`）而不是編輯器手拉：格數與 cell 尺寸是 `--height`
的函數，手拉的話每次改尺寸都要重來，而且會**靜默地對不上**（region 還指著
舊的 cell 尺寸，畫面歪掉但不報錯）。

**只有 `run` 是真動畫。** 素材只有跑步循環這 8 格，`idle` 借格 1、`jump`
借格 5（騰空姿勢）。站著不動或滯空時繼續播跑步會很怪，凍住反而讀得出來。

判斷順序：滯空優先於水平速度，否則跳躍中按著左右鍵會播成跑步。

### `body_color` → `tint`

owner 決定：一隻保留原色，另一隻隨意。

`ColorRect` 換成貼圖之後兩隻貓會長得一模一樣，原本靠 `ColorRect.color`
區分兩人的機制失效，改用 `modulate` 相乘染色。連帶把 `body_color` /
`set_body_color()` 改名 `tint` / `set_tint()` —— 現在的語意是相乘染色而不是
「身體的顏色」，舊名字會誤導。

P1 用 `Color.WHITE` = 不染，保留美術原色；P2 染藍（沿用舊配色的那個藍）。
相乘染色在黑貓身上**只吃得到亮部**（連帽衫、球鞋、墨鏡），黑色身體不受影響
—— 這反而是好事：兩隻剪影一致，只有配色不同。

改名要動三處：`player.gd`、`level.gd` 的 `PLAYER_COLORS`、以及
**`main.tscn` 裡兩個 Player 實例的 export 覆寫**（第三處差點漏掉）。

## 步驟 19：去背門檻是錯的 —— 角色被自己的描邊切碎

owner 回報「手臂和尾巴破圖」，並懷疑是來源圖有問題。**來源沒有問題。**

### 診斷過程

跑了四項診斷，結論與最初推測不同：

| # | 診斷 | 結果 |
|---|---|---|
| 1 | 來源連通結構 | **每格被切成 18-33 塊**，頭與身體分離（格 3,4,5,6,8）|
| 2 | 去背門檻掃描 | 門檻 20 只保留角色的 33-60%；降到 4-6 是 96-99%，臨界點在 8 |
| 3 | 二值化危險區 | 門檻 20 時 21.6% 的實心像素在擲骰子；門檻 6 降到 11.0% |
| 4 | 去屑對照 | 只刪掉 12 個單像素（0.3%），**不是主因** |

一度從「去屑數 22px 時 2 塊、44px 時 12 塊」推論是二值化打斷細部再被去屑
清掉。方向對（44px 確實碎得多），但**量級錯了** —— 每格 1-3 個單像素不足以
造成看得見的破圖。診斷 1 才是真的。

### 根因

這張圖是正統像素美術畫法：**用黑色線條給每個部件描邊**（耳朵、墨鏡、眼睛、
連帽衫、手臂、褲子、球鞋全都有）。而那些描邊的亮度跟背景一樣是黑的。

去背規則是「暗 + 與畫布邊緣相連 = 背景」，於是 flood fill **把角色自己的
描邊當成通道**，從輪廓的缺口鑽進去，沿著描邊把整隻貓的內部啃穿。

視覺化證據：把「門檻 20 判成背景、門檻 6 判成前景」的像素標成洋紅，
標出來的形狀**精確重現了這張圖的描邊線稿**。格 4 被多吃掉 3569px，
佔該格角色的 **11.7%**；脖子的描邊一斷，頭就跟身體分家。

尾巴和手臂最明顯，因為它們本來就細，描邊沒了就散架。

### 最重要的一課：驗證指標偵測不到它要抓的失敗模式

當初選門檻 20 的理由寫在程式碼註解裡：「實測 fg 佔 33.5%，合理」。

**前景百分比在「角色完好」與「角色被切成 30 塊」兩種情況下看起來一樣合理**
—— 面積對了，拓樸壞了。面積類指標永遠測不出連通性問題。

而且工具原本就印「封閉暗區 801 塊」，那正是被啃穿後殘留的碎片。**報告有印，
但沒有判準說多少算不正常，所以被跳過了。報告數字而不給判準等於沒報告。**

### 修法

三件事一起做：

1. **門檻由資料推導，不寫死。** 掃描門檻階梯，用「主連通塊佔角色面積的
   比例」找崩塌轉折點，取轉折點以下但盡量靠近它的值（門檻越低，留在角色
   周圍的背景暈影越多，輪廓會虛胖）。這張圖自動選出 **4**。
   為什麼要自動：這個值完全取決於來源怎麼畫。換一張沒描邊、或背景不是純黑
   的來源，臨界點會完全不同 —— 寫死的魔術數字換張圖就會再爆一次，而且
   爆得很安靜。
   實作用兩段式：先用極保守的門檻 2 定出橫帶與格邊界（這兩件事對門檻不敏感），
   再固定格邊界掃描比較。
2. **逐格連通性健檢，帶判準。** ≥90% OK、70-90% 注意、<70% 「角色被切碎」。
3. **去屑回報位置而不只數量。** 光看「刪了 12 塊」分不出是雜訊還是尾巴尖。

結果：實心像素 5300 → 5995（**+13.1%**），完整性 95-99%，去屑從 12 塊降到 6 塊。

## 步驟 20：順帶修掉的 `.tres` 路徑推導

`--godot-frames` 產出的 `res://` 路徑原本是字串裁切，`--out` 指到專案目錄外
時會產出 `res://C:/Users/...` 這種永遠載不到的路徑，**而且不報錯**。
改成 `relative_to(cwd)`，在專案外時明確 `SystemExit`。

# 環境知識

- `py -3` = Python 3.13.5；numpy 2.4.6 有，**Pillow 沒有**。
  裸 `python` 是 Microsoft Store 的 stub（`tools/serve.py` 的 docstring 已記載）。
- Godot `4.7.2.stable`，`AppData/Local/Microsoft/WinGet/Links/godot` 在 PATH 上。
- `Path.write_text()` 在 Windows 上預設把 `\n` 轉成 `\r\n`，但本專案
  `.gitattributes` 是 `eol=lf`。工具寫檔一律帶 `newline="\n"`。
- headless 截圖可行：`godot --path . --script <SceneTree 腳本>`，在
  `_process` 裡 `root.get_texture().get_image().save_png()`。**要真的開視窗**
  （不能加 `--headless`），dummy renderer 產不出圖。
- 模擬輸入要走 `Input.action_press()`，**直接寫 `velocity.x` 沒用** ——
  `_physics_process` 每幀都會用 `Input.get_axis()` 覆蓋掉它。
- `--debug-collisions` 可以把碰撞框畫進 SubViewport，會被合成層帶出來。

# 已知問題

- **來源圖有生圖殘留的浮空碎片**：脫離角色、飄在背景中的小鰭狀物（形狀跟
  尾巴尖一樣，等於生圖時多丟了一片尾巴碎塊），來源解析度下 118-475px，
  幾乎每格都有。**owner 決定不在管線裡加清理規則**，等乾淨的來源圖再說。
  已量過距離分布可供之後參考：合法的分離部件（被描邊隔開的耳朵、手、腳）
  離主體 ≤5px，浮空垃圾 ≥16px，兩群分得很開，尾巴本身是連在主體上的。
- `art/player/cat_run_preview.png` 是給人眼驗收用的，但它在 Godot 的 import
  路徑裡，44KB 會被打包進 web 匯出的 `.pck`。乾淨的做法是把預覽產到一個
  掛 `.gdignore` 的資料夾。
- `--min-blob 2` 刪掉的是單像素。目前 6 塊，位置已印出但沒人逐一確認過
  那不是尾巴尖。
- 44px 下二值化仍有 11.0% 的實心像素落在 alpha 0.25-0.6 的危險區間。
  這是取樣定理的限制（次像素寬度的結構無法在二值點陣上穩定表示），
  不是調參能消除的。真要處理是「二值化保連通性」或手工修圖。
